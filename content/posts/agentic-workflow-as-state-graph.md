Agentic Workflow 很容易被讲成“让大模型自己干活”。但真正做系统时，这个说法太粗。更稳的理解是：把任务执行过程建模成一个状态图，模型只是其中的策略节点，工具、记忆、检查器和人工反馈共同决定图上的状态转移。

如果只把大模型当成一个黑盒入口，系统会很快失控：上下文会漂移，工具调用会重复，错误会被后续步骤放大，最后甚至不知道是哪一步把事情带偏了。状态图视角的价值，是把“智能”拆成可观察、可暂停、可回滚的执行结构。

## 从线性流程到状态图

一个最简单的自动化流程可以写成：

\[
u \rightarrow p \rightarrow a \rightarrow o,
\]

其中 \(u\) 是用户目标，\(p\) 是计划，\(a\) 是动作，\(o\) 是输出。这种线性结构适合一次性问答，但不适合长任务。长任务更像一个有环图：

\[
G=(S,E,\pi,\mathcal T),
\]

其中 \(S\) 是状态集合，\(E\) 是可转移边，\(\pi\) 是策略，\(\mathcal T\) 是工具集合。每一步执行不是简单生成下一段文本，而是选择一个状态转移：

\[
s_{t+1}=F(s_t,a_t,r_t),
\]

\(a_t\) 表示当前动作，\(r_t\) 表示工具或环境返回结果。这个公式的关键不是数学复杂，而是提醒我们：智能体必须读结果、更新状态，而不是盲目连续输出。

## 状态里应该放什么

状态不等于聊天记录。聊天记录通常太长，也混入了大量对当前决策无用的信息。更实用的状态可以拆成四层：

1. 目标状态：用户最终要什么，哪些约束不可破坏。
2. 工作状态：当前已经完成什么，下一步阻塞在哪里。
3. 证据状态：哪些判断来自文件、日志、网页、实验结果。
4. 风险状态：哪些地方可能错，哪些操作需要人工确认。

如果用符号表示，可以写成：

\[
s_t = \{g, c_t, e_t, r_t\},
\]

其中 \(g\) 是稳定目标，\(c_t\) 是当前上下文，\(e_t\) 是证据集合，\(r_t\) 是风险集合。好的工作流会尽量让 \(g\) 稳定，让 \(c_t\) 精简，让 \(e_t\) 可追溯，让 \(r_t\) 显式化。

## 任务分解不是越细越好

任务分解常见问题是过度拆分。拆太粗，模型容易遗漏步骤；拆太细，系统会把大量时间花在协调和状态同步上。更好的拆分标准是：每个子任务应该有明确输入、明确完成条件和可独立验证的输出。

可以把子任务 \(i\) 的价值写成：

\[
V_i = Q_i - \lambda C_i - \mu R_i,
\]

其中 \(Q_i\) 是完成后带来的信息增益或进度收益，\(C_i\) 是上下文切换和工具调用成本，\(R_i\) 是失败风险。拆分不是为了显得有条理，而是为了提高 \(V_i\)。

例如“改造博客 UI”可以拆成：

- 读取主题结构和现有模板；
- 设计首页、列表页、文章页的信息结构；
- 修改 CSS 和布局；
- 生成或选择图片资产；
- 本地构建和浏览器验证；
- 提交、推送、检查部署。

这些子任务之间有依赖，但每一步都有可检查结果。相比之下，“优化一下博客”太抽象，“把每个 CSS 选择器都拆成一个任务”又太碎。

## 工具边界决定可靠性上限

Agentic 系统的可靠性不只取决于模型能力，也取决于工具边界。一个工具最好满足三个条件：

- 输入结构化：不要让模型用自然语言猜参数。
- 输出可验证：返回状态码、文件路径、摘要或 diff。
- 副作用可控：写文件、删除文件、发布内容等动作要有边界。

工具调用可以看成从状态到观测的映射：

\[
o_t = T_k(a_t, s_t),
\]

模型真正该做的是根据 \(o_t\) 更新判断，而不是假设工具成功。很多自动化事故来自“工具失败了，但模型继续按成功路径走”。所以状态图里应该显式存在失败边：

\[
s_t \xrightarrow{T_k=\mathrm{fail}} s_{\mathrm{repair}}.
\]

这个修复状态可能是重试、换工具、缩小任务，或者请人确认。

## 记忆：不要保存一切

长期记忆很诱人，但“全都记住”通常会制造噪声。更合理的记忆是摘要化、结构化和带有效期的。

我更倾向于把记忆分成三类：

- 项目记忆：目录结构、构建命令、发布流程。
- 偏好记忆：用户喜欢的风格、命名方式、输出粒度。
- 决策记忆：为什么选 A 不选 B，之后出现问题时能追溯。

记忆写入也应该有门槛。可以用一个简单规则：

\[
\mathrm{write}(m)=\mathbb{1}[I(m)>\tau_I \land R(m)<\tau_R],
\]

只有信息价值足够高、隐私或安全风险足够低的内容才进入长期记忆。比如 API key、账号密码、临时 token 就不应该写入项目文件，也不应该进入公开文档。

## 可观测性比“聪明”更重要

长任务中，最危险的不是模型偶尔犯错，而是错误发生后系统没有暴露出来。可观测性至少包括：

- 每一步做了什么；
- 依据是什么；
- 改了哪些文件；
- 测试或构建是否通过；
- 还有哪些残余风险。

如果把一次执行看成轨迹 \(\tau\)：

\[
\tau = (s_0,a_0,o_0,s_1,\ldots,s_T),
\]

那么可观测性就是让轨迹可以被人快速检查。一个好的 agentic workflow 不应该让人读完整段聊天才能理解结果，而应该在关键节点留下结构化证据。

## 一个实用设计原则

我现在更愿意把 Agentic Workflow 设计成“保守执行器”，而不是“完全自治体”。它可以主动推进任务，但需要在高风险节点停下来；它可以写代码和整理文章，但必须能构建验证；它可以生成图片，但不能把密钥写进仓库。

真正有用的智能体不是看起来多会聊天，而是能在复杂任务里保持上下文、尊重边界、留下证据，并把不确定性压到可管理范围内。
